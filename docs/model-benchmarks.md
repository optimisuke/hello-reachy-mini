# 直接APIバックエンドのモデル選定（実測 2026-08-30）

`reachy_mini_conversation_app` の `CONVERSATION_BACKEND=direct` で使う STT / LLM / TTS を、
**実APIに投げて測って**選んだ記録。判断基準は「コスパよく、そこそこ動いて、反応が滑らか」。
価格は 2026-08-30 時点の <https://developers.openai.com/api/docs/pricing>。

## 結論

| 段 | 採用 | 理由 |
| --- | --- | --- |
| STT | `gpt-transcribe` | 句読点まで完全一致。`gpt-4o-transcribe` と同レイテンシで**より安い**（$0.0045 vs $0.006/分） |
| LLM | `gpt-5.4-mini` | 最初のトークンまで 0.46〜0.52s で候補中最速。日本語も自然 |
| TTS | `gpt-4o-mini-tts`（日付なしエイリアス） | 日付固定に速度上の優位が無かった。エイリアスなら自動で新しくなる |

**1ターンあたり約 $0.0016（0.16円強）＝ 1ドルで約610ターン。**

## 測り方

計測は使い捨てスクリプトで、アプリの実モジュール（`speech_services` / `audio.pcm` /
`prompts` / `core_tools`）を import して**実際に通る経路**を叩いた。リポジトリには入れていない。

- 日本語プロファイル `default_ja` の system プロンプト（1,886文字）＋**ツール17個**を毎回積む
- STT の評価は「TTS で日本語を合成 → 16kHz にリサンプル → 文字起こし」の往復で、元の文と比較
- LLM は streaming で **最初のトークンまでの時間 (TTFT)** を測る。音声ループでは
  TTFT が「喋り始めるまで」に直結するので、合計時間より重要
- `stream_options={"include_usage": True}` でトークン消費とキャッシュヒットを取得

⚠️ **合成音声で測っているので、実マイクでの認識精度は別問題。**
無音は完全な無音、残響なし、音量一定という理想条件。実機での確認が別途必要。

## LLM の TTFT

日本語プロファイル＋17ツールを積んだ状態。

| モデル | 挨拶 TTFT | ツール要求 TTFT | 備考 |
| --- | --- | --- | --- |
| **gpt-5.4-mini** | **0.52s** | **0.47s** | 採用。`dance` を正しく呼ぶ |
| gpt-5.4-nano | 0.64s / 1.08s | 0.72s | mini より遅い。応答もやや冗長 |
| gpt-4.1-mini | 0.73s | 0.71s | — |
| gpt-4o-mini | 0.95s | 0.45s | 当初の設定 |
| gpt-5.5 | 1.22s | 0.90s | 遅い。挨拶で余計に `play_emotion` を呼ぶ |
| gpt-5.6-luna | ✗ | ✗ | **400: "Function tools with reasoning_effort are not supported"** |

- **nano は mini より安いが遅い**。価格の安い方が速いとは限らない
- `gpt-5.6` 系は現在のツール構成では使えない（reasoning 系の制約）
- gpt-5.4-mini / nano の `reasoning_tokens` は **0**。今の呼び方では reasoning の
  遅延オーバーヘッドは乗っていない

## トークン消費とプロンプトキャッシュ

1ターンの実測（`usage` より）:

```text
input 2,593〜2,629 tokens   うち cached 2,176 tokens
output 8〜30 tokens         （プロファイルが短い返答を強制しているため）
```

**入力の 8割以上がキャッシュヒットしている。** system プロンプト＋ツール定義という
不変の接頭辞が自動キャッシュに乗るため。効果は小さくない:

| モデル | キャッシュあり | キャッシュなし |
| --- | --- | --- |
| gpt-5.4-mini | $0.000577 | $0.002063 |
| gpt-5.4-nano | $0.000155 | $0.000551 |

つまり**キャッシュが LLM コストを約1/4にしている**。ツールを増やすと接頭辞が伸びるが、
不変であればキャッシュに乗るので、増分の影響は思ったより小さい。

## 1ターンのコスト内訳

「4秒聞いて3秒喋る」を1ターンとした場合:

| 段 | モデル | コスト | 比率 |
| --- | --- | --- | --- |
| STT | gpt-transcribe（$0.0045/分） | $0.00030 | 18% |
| LLM | gpt-5.4-mini | $0.00058 | 36% |
| TTS | gpt-4o-mini-tts（$12/1M audio tokens ≒ $0.015/分と見積り） | $0.00075 | 46% |
| **合計** | | **$0.00163** | **1ドルで約610ターン** |

読み取れること:

- **音声（STT+TTS）が 64% を占める。LLM はコストの主役ではない。**
  だから LLM は「安い方」より「速い方」を選ぶのが正しい
- mini → nano への変更で浮くのは **1ターンあたり $0.00042**。
  全体の26%だが、絶対額は0.04セント。滑らかさを捨てる価値はない
- TTS の見積りだけ精度が低い（`/v1/audio/speech` は `usage` を返さないため、
  audio token 数を実測できていない）

## 実際の請求額（2026-08-30 実測）

**1日つかって $0.56。** 見積り（1ターン $0.00163）と整合する。

この $0.56 に含まれるもの:

- 実機での日本語会話（監視できた範囲で60〜70発話。カメラ・ダンス・記憶ツールを含む）
- モデル選定のベンチマーク（chat 6モデル × 2プロンプト、TTS 4モデル、STT 4モデル、`ja`/`jp`/`en` の比較）
- ローカルからの結線確認（フェイクサーバ経由の全段テスト、実APIでの往復テスト数回）

つまり**会話そのものより検証のほうが多く使っている**状態でこの額。会話だけなら見積りどおり
1ドルで600ターン前後のはず。子どもと遊ぶ用途なら、月に数ドルで収まる見込み。

⚠️ ただし**カメラを使うと跳ねる**。一度撮ると画像が履歴に残って以降のターンで再送されるため、
画像トークンが毎ターン乗る（未修正の項目）。カメラを多用したセッションはこの見積りを超える。

## さらにコストを詰めるなら

LLM を **HF router の `Qwen/Qwen3-4B-Instruct-2507`**（リポジトリの既定）に戻すと:

| 構成 | 1ターン | 1ドルあたり |
| --- | --- | --- |
| gpt-5.4-mini | $0.00163 | 約610ターン |
| Qwen3-4B（HF router） | $0.00108 | 約928ターン |

LLM 段が実質ゼロ（$0.000027/ターン）になる。ただし:

- `HF_TOKEN` が必要（このMacには未設定なのでレイテンシ未計測）
- 日本語応答・Function Calling・SSE は**実機で確認済み**
- 切り替えは `.env` から `DIRECT_LLM_BASE_URL` と `DIRECT_LLM_MODEL` の2行を消すだけ

まず実機で動かす段階では不確定要素を減らしたいので gpt-5.4-mini を採用。
安定したら Qwen に落とすのが筋。

## STT の比較

同一音声（「明日の予定を教えて。あと、ダンスも踊ってほしいな。」5.5秒）を文字起こし:

| モデル | 時間 | 結果 | 価格 |
| --- | --- | --- | --- |
| **gpt-transcribe** | 0.72s | `明日の予定を教えて。あと、ダンスも踊ってほしいな。` | $0.0045/分 |
| gpt-4o-transcribe | 0.72s | `明日の予定を教えて、あとダンスも踊ってほしいな。` | $0.006/分 |
| gpt-4o-mini-transcribe | 0.60s | `明日の予定を教えて、あと、ダンスも踊ってほしいな。` | $0.003/分 |
| gpt-live-transcribe | ✗ | 404（`/v1/audio/transcriptions` のモデルではない） | — |

`gpt-transcribe` だけが句読点を完全再現。**句読点は文分割（TTS に送る単位）に直接効く**ので、
ここは精度を取った。しかも `gpt-4o-transcribe` より新しく安い。

### `language` は `ja`（`jp` ではない）

ISO-639-1 の2文字コード。実際に投げた結果:

```text
language='ja' -> '明日の天気を教えて。'
language='jp' -> 400 BadRequest: "Language code 'jp' is not recognized."
language='en' -> '明日の天気を教えて。'   ← 間違った指定でも自動判定で通る
language=''   -> '明日の天気を教えて。'
```

`en` のままでも日本語が返るのは自動判定が効いているから。**ヒントに過ぎない**が、
指定した方が精度・遅延に有利。`REALTIME_TRANSCRIPTION_LANGUAGE=ja` がこの値になる。

## TTS の比較

| モデル | 合成時間 | 出力長 | 判断 |
| --- | --- | --- | --- |
| **gpt-4o-mini-tts** | 1.77s → 再測定 - | 5.90s → 5.25s | 採用（エイリアス） |
| gpt-4o-mini-tts-2025-12-15 | 1.25s → 再測定 - | 4.55s → 5.50s | 差はノイズだった |
| tts-1 | 2.73s | 3.79s | 古い |
| gpt-audio-mini | ✗ | ✗ | 404（chat API 側のモデル） |

**1回目の測定では日付付きスナップショットが速く見えたが、再測定で差が消えた。**
1回の測定で日付を固定していたら、根拠のない pin を残すところだった。
両方とも取りこぼしなし、24kHz 前提も成立（リサンプル後の文字起こしがクリーン）。

`gpt-4o-mini-tts` は `$12/1M audio tokens`＋テキスト入力 `$0.60/1M`。
`/v1/audio/speech` は `usage` を返さないので、audio token の実測はできていない。

## 未計測・要確認

- 実マイクでの STT 精度（合成音声はクリーンすぎる）
- VAD 閾値 `DIRECT_VAD_*` の実環境での妥当性
- TTS の audio token 実数（コスト見積りの精度）
- Qwen3-4B の TTFT（HF トークンが必要）
- CM4 上での CPU 負荷（VAD は 20ms 窓の RMS だけなので軽いはずだが未確認）
