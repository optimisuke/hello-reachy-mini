## 解決済み（記録として残す）

### 1. 顔追跡（解決）

状態: 解決（2026-08-29）

原因: daemon側のtrackerは自分でカメラを開かず、GStreamerの `unixfdsrc` で共有カメラ
フィードへ接続する実装だった。`media_backend="no_media"` ではそのフィードが配信されず、
tracker はフレームを1枚も受け取れないため `detected` が永久に `False` になっていた。
SDKやハードウェアではなく、こちらのスクリプトのバグ。

修正: `ReachyMini(media_backend="default")` にする。

検証結果:

- 本体上、同一スクリプトでの比較: `no_media` 0/15（0%）→ `default` 12/15（80%）
- Mac版 `face_tracking.py` も同じ1行修正で24/30（80%）検出
- どちらも実機の頭が顔を追って動くことを目視確認した

詳細は `docs/sdk-test-notes.md` の「顔追跡（原因確定・解決 2026-08-29）」を参照。

## 最優先: 未解決タスク

### 2. Mac生成WAVの音声再生が失敗する（原因を送信経路まで絞り込み）

状態: 調査中（原因はMac→本体の音声送信経路に絞られた）

確認済み:

- Macの `say` でWAVを生成するテストは音が鳴らず、プロセスも終了しなかった
- 本体内蔵の `wake_up.wav` と `go_sleep.wav` は正常に再生できる
- カメラのWebRTC接続は成功する
- Mac生成WAVはHTTPでアップロードし、HTTPで再生開始を指示する実装
- 本体上（`localhost_only`）からの `play_sound()` は成功し、スピーカーから音が鳴った。
  ハングもせず終了コード0。daemon・音声デバイス・スピーカー・APIは正常と確定した
- したがって失敗要因は「Mac→本体の音声送信経路」か「Mac生成WAVの形式」に絞られた

確定した事実（2026-08-30）:

- Mac生成WAVを `scp` で本体へ送り、本体上で再生したら**正常に音が鳴った**
- したがってWAV形式（mono / 16000 Hz / 16bit PCM）は無罪
- **原因はMac→本体の音声送信経路（WebRTC）に確定**

次に試すこと:

1. Mac版にflush付きログを入れ、アップロードと再生要求のどちらで止まるか特定する
2. 各処理にタイムアウトを設定し、ハングの箇所を確定する
3. Mac版実行中のdaemonログを取得する（顔追跡同様、固有の警告が出る可能性）
4. 顔追跡の教訓を踏まえ、引数を既定値のまま実行して比較する

完了条件:

- Macで生成した音声が本体スピーカーから再生される
- スクリプトが一定時間内に正常終了する
