## 1. M5Stack Stopwatch（ESP32）から Reachy Mini を操作する

### やりたいこと

M5Stack Stopwatch（ESP32ベース）のボタンやセンサーで Reachy Mini を動かす。
Mac を介さず、デバイス単体からロボットへ指示を送る。

### 技術的な裏付け（2026-08-30 調査済み）

**結論: 本体側にHTTPプロキシを置く構成で行く（下記「方針」）。**

調査の出発点として、SDKが特別なプロトコルを使っておらず**WebSocketにJSONを投げている
だけ**だと分かった。ただしこれは文書化されていない内部APIなので、直接叩くのは避ける。

- 接続先: `ws://reachy-mini.local:8000/ws/sdk`
  （`reachy_mini/io/ws_client.py` の既定 host=localhost, port=8000）
- 送信内容: pydanticモデルを `model_dump_json()` した**素のJSON**
- **訂正**: 当初「RESTにモーション系エンドポイントは無い」と記録したが誤りだった。
  実際には `POST /api/move/goto`、`POST /api/move/set_target`、
  `POST /api/move/play/recorded-move-dataset/{dataset}/{move}`、`GET /api/move/running`、
  `POST /api/move/stop` などが存在し、**実機で叩けることを確認済み**

実際のJSON例（SDKが送っているものそのまま）。

```json
{"type":"play_recorded_move","move_name":"simple_nod","dataset_name":null,"initial_goto_duration":0.0}
{"type":"set_antennas","antennas":[0.1,0.2]}
```

コマンドは50種類以上ある（`reachy_mini.io.protocol` の `*Cmd`）。ESP32から使いそうなもの:

| コマンド | 用途 |
| --- | --- |
| `goto_target` | 頭・アンテナ・胴体を指定姿勢へ（`head`, `antennas`, `duration`, `body_yaw`） |
| `set_antennas` | アンテナだけ動かす |
| `set_body_yaw` | 胴体回転 |
| `play_recorded_move` | ダンス・感情モーションを名前で再生 |
| `play_sound` | 内蔵音源の再生 |
| `set_head_tracking` | 顔追跡のON/OFF |
| `wake_up` / `goto_sleep` | 起床・就寝 |
| `set_torque` / `set_motor_mode` | モーターの有効・無効 |

### 公式に文書化されている経路と、そうでない経路

| 経路 | 対象 | 文書化 |
| --- | --- | --- |
| Python SDK | Python | 公式ドキュメントあり |
| JavaScript SDK | ブラウザ | 公式ドキュメントあり。**WebRTC**で接続。公式は「新しいアプリはこれが推奨」と明記 |
| REST API `:8000` | 任意 | OpenAPIから発見できる。**モーション系も存在する**（`/api/move/*`）。公式ドキュメントには記載なし |
| `ws://:8000/ws/sdk` | 任意 | **文書化なし**（SDKのソースを読んで判明した内部API） |

公式が非Pythonクライアント向けに用意しているのはJS SDK + WebRTCだが、**ESP32には重すぎる**
（DTLS/SRTP、ICE、SDPネゴシエーション、HuggingFace OAuthが必要）。

### 方針: 本体側にプロキシAppを置き、HTTP RESTを公開する（採用）

ESP32から直接WebSocketを叩く案もあるが、`/ws/sdk` は内部APIなのでSDK更新で壊れうる。
**本体上でプロキシを動かし、公式のPython SDKを内部で使う**構成にすれば、公開APIの上に
乗るので安定する。ESP32側も素のHTTPだけで済み、実装が最小になる。

```text
┌──────────┐  HTTP (LAN)   ┌──────────────────────────────┐
│  ESP32   │ ────────────▶ │ Reachy Mini 本体             │
│ M5Stack  │  GET /move/…  │  プロキシApp (FastAPI)        │
│ Stopwatch│               │       │ Python SDK           │
└──────────┘               │       ▼ localhost_only       │
                           │  daemon → モーター・音声      │
                           └──────────────────────────────┘
```

**採用理由**

- ESP32側はHTTP GETだけ。WebSocketもJSONパースも不要にできる
- 姿勢計算（4x4行列など）をPython側に寄せられる。ESP32で行列を作らなくてよい
- 内部APIに依存しないので、SDK更新で壊れにくい
- 同じネットワーク内で完結し、インターネットやOAuthを経由しない
- Appとして常駐させれば、電源投入後すぐ使える

**設計メモ**

- App化は `docs/tasks.md` の E-4 と同じ作業になる。先にE-4を片付けると近道
- **FastAPIとuvicornは本体の `apps_venv` に既にある**（0.141.1 / 0.52.4）。
  daemon自身がFastAPIなので追加インストールは不要
- 本体内から `ReachyMini(connection_mode="localhost_only")` で接続する
- ポートはdaemonの8000を避ける。8080は現在未使用だった
- 接続は**起動時に1回張って保持**する。リクエストごとに接続すると遅い
- ESP32からの宛先は `reachy-mini.local`（mDNS）かIP。ESP32のmDNSは不安定なことが
  あるのでIP直指定も選べるようにする
- `PUT /api/apps/startup-app` で自動起動に設定できる
- LAN内限定でも、簡単なトークンをクエリかヘッダに入れておくと安心

**エンドポイント案**

| メソッド | パス | 動作 |
| --- | --- | --- |
| GET | `/move/{name}?library=emotions` | ダンス・感情モーションを名前で再生 |
| GET | `/moves` | 再生できるモーション名の一覧 |
| GET | `/antennas?left=30&right=-30` | アンテナを度で指定 |
| GET | `/body_yaw?deg=20` | 胴体回転 |
| GET | `/head?roll=0&pitch=-10&yaw=0` | 頭の姿勢を度で指定 |
| GET | `/sound/{name}` | 内蔵音源の再生 |
| GET | `/tracking/{on\|off}` | 顔追跡の切り替え |
| GET | `/state` | 現在姿勢とモーター状態 |
| GET | `/wake` `/sleep` | 起床・就寝 |

すべてGETにしておくと、ESP32側は1行で書ける。

```cpp
http.begin("http://192.168.x.x:8080/move/laughing1?library=emotions");
http.GET();
```

**排他制御についての注意**

Appとスクリプトは同時にロボットを操作できない（`GET /api/daemon/robot-app-lock-status`
で状態が見える）。プロキシをAppとして常駐させると、**プロキシがロックの持ち主になる**。
他のスクリプトを動かしたいときはプロキシを止める必要がある（要検証）。逆に、プロキシ経由に
操作を集約すれば競合は起きない。

### 代替案（採用しない理由も含めて記録）

**案B: ESP32から `/ws/sdk` を直接叩く**

- 送信内容は素のJSON1行なので実装は簡単
- ただし**内部APIで無保証**。SDK更新で壊れる可能性がある
- 中継が不要という利点はあるが、安定性を優先してプロキシ案を採る

**案C: MQTTなどを挟む**

- 複数デバイスへ広げるなら検討。今は過剰

**案D: JS SDK + WebRTC**

- 公式推奨だがESP32には重すぎる。ブラウザから操作したくなったらこちら

### 進捗: プロキシは実装・動作確認済み（2026-08-30）

`reachy_proxy.py` として実装し、本体上で動かしてMacから全エンドポイントを叩けることを
確認した。詳細は `docs/sdk-test-notes.md` の「REST APIプロキシを本体で動かす」を参照。

- ダンス・感情モーション（音付き）・アンテナ・胴体回転・頭・内蔵音源・状態取得が動作
- `wait=false` で長いモーションでも**0.15秒**で応答（17.26秒のモーションを非同期再生）
- 再生中の二重要求は409、`/cancel` で中断可能
- 実装上の注意は上記メモに記録（ロックの範囲、`async_play_move` の罠など）

**daemonのRESTを直接叩く選択肢も判明した**（`/api/move/*` が存在する）。それでも
プロキシを置く価値は残る。角度を度で受けられる、エンドポイントが単純、データセット名の
URLエンコードを隠せる、複数操作をまとめられる。

### 残っている一歩

1. ESP32から同じURLをGETする
2. ボタンごとにモーションを割り当てる
3. App化して自動起動にする（E-4）
4. 認証（簡単なトークン）を足すか判断する

### 未検証・確認したいこと

- プロキシAppがロックを持つと、他のスクリプトが動かせなくなるか
- ~~本体でFastAPIを動かすための依存~~ → **確認済み。`apps_venv` に FastAPI 0.141.1 と
  uvicorn 0.52.4 が入っている**（daemon自身がFastAPIで動いているため）。追加インストール不要
- Appの実行環境で任意のポートを開けるか
- ESP32のmDNSで `reachy-mini.local` を解決できるか
- 連続リクエスト時の応答時間（モーション中に次のリクエストが来た場合の挙動）

### やると面白そうなこと

- Stopwatchのボタンで感情モーションを切り替える（85種類あるのでランダム再生も楽しい）
- 経過時間に応じてロボットの様子が変わる（待たされて `impatient1`、完了で `success1`）
- Stopwatchを傾けるとロボットも同じ方向へ首を傾ける（IMU連携）
- ポモドーロタイマー化して、休憩時間に踊る

## 2. 日本語で会話できるようにする

### やりたいこと

Reachy Mini と日本語で会話する。公式の会話アプリ
（`reachy_mini_conversation_app`）は英語前提の構成になっている。

### 現状（調査済み・詳細は `docs/sdk-test-notes.md`）

すでに調査と実機テストを済ませており、**失敗の原因まで確定している**。

- LLMはロボット本体では動かない。外部バックエンドへ投げる構成
- プロトコルはOpenAI互換だが、OpenAIではない
- 構成はe2eではなく **VAD → STT → LLM → TTS のカスケード**
- **日本語音声が欧州言語として文字起こしされる**のが最大の障害。原因は確定済み
- 出力側（TTS）は日本語に対応していた
- `deployed` バックエンドは**段単位での差し替えができない**
- インスタンスディレクトリと `.env` の場所は実機で確認済み（アプリ更新で消える点に注意）

### 実装の選択肢（調査済みの案）

**案1: STTを外部APIへ出す（未実施）**

- `--stt` フラグでSTTだけ差し替える構成が実装から確認できている
- OpenAIホストのSTTを使う例まで整理済み
- コスト注意点、起動時のチェック挙動、実行場所の選択肢も調査済み
- **これが本線候補**

**案2: `--stt none` で音声を直接LLMへ渡す**

- 実装上は可能。日本語の扱いがどうなるかは未検証

**案3: ローカルバックエンドへ切り替える**

- 可能だがCM4でSTTを動かせるかが課題（調査済み、厳しそう）

**案0: プロファイルの言語設定だけ変える → 失敗（原因確定済み）**

- 設定は読まれていたが、STT側の言語判定で日本語が別言語になった

### 次にやること

1. 案1（STTをOpenAI APIへ出す）を実機で試す
2. 日本語の認識精度と、ターン遅延（実測値は既に記録あり）を比較する
3. できるだけ無料で日本語対応させる選択肢（調査済み）と、実測コストを突き合わせる

### 発展させたいこと

- 会話に感情モーションを紐付ける（85種類あるので、返答の感情に合わせて動かす）
- `enable_wobbling()` で喋っているように頭を揺らす（`docs/tasks.md` C-3）
- 音源方向推定（DoA）で、話しかけた人の方を向いてから返答する（C-2）
- 顔追跡と組み合わせて、会話中は相手を見続ける

## 3. 描いた絵を見せて、AIに感想やアドバイスをもらう

### やりたいこと

紙に描いた絵を Reachy Mini のカメラで撮り、AIに読み取らせて、キャプション・感想・
アドバイスを**声で返してもらう**。以前アプリ経由で似たことをやったが、Reachy Mini なら
「絵を覗き込む → 反応する → 喋る」という一連の動作込みで表現できる。

### 処理の流れ（案）

```text
1. 頭を下げて絵を覗き込む      goto_target(pitch=+n)
2. カメラで撮影                media.get_frame_jpeg()
3. 画像をAIへ送る（Vision）    キャプション・感想・アドバイスを日本語で生成
4. テキストを音声化（TTS）      16 kHz モノ 16bit PCM WAV へ
5. スピーカーで再生            media.play_sound()
6. 感情に合った動きを添える     play_move("proud1" / "amazed1" など)
```

### 実現手段の裏付け（2026-08-30 調査済み）

本体上（`apps_venv`）に必要なものが揃っている。**追加インストールなしで着手できる。**

| 用途 | 使えるもの | バージョン |
| --- | --- | --- |
| 画像取得 | `media.get_frame_jpeg()`（JPEGバイト列） | 検証済み |
| 画像処理 | Pillow / OpenCV | 12.3.0 / 4.14.0.94 |
| API呼び出し | `openai`（OpenAI互換API用）、`requests`、`httpx` | 2.28.0 / 2.34.2 / 0.28.1 |
| HF連携 | `huggingface_hub`、**HFトークンはログイン済み** | 1.29.0 |
| 音声再生 | `media.play_sound()` | 検証済み |
| 感情表現 | 感情モーション85種（音付き） | 検証済み |

### 検討ポイント

**AIをどこで動かすか**

- 外部API（クラウド）が現実的。CM4でVisionモデルを回すのは厳しい（会話アプリの調査でも
  同じ結論だった）
- 選択肢: OpenAI互換API（`openai` パッケージが既にある）、HF Inference API
  （トークン設定済みなのでそのまま使える）、Claude API（`anthropic` は未導入だが
  `httpx` で直接叩ける）
- 具体的なモデルと料金は選定時に確認する（要調査）

**TTS（テキスト→音声）が課題**

- 本体には macOS の `say` に相当するものが無い（`gtts`、`pyttsx3`、`piper-tts` いずれも
  未導入）
- 選択肢
  1. **外部のTTS APIを使う** — 実装は簡単。ネットワーク必須
  2. **Macで音声を作って本体へ送る** — Macの `say` は日本語も出せる。すでに実績あり
     （`audio_playback.py`）。ただしMacが必要になる
  3. **軽量TTSを本体へ導入する** — `piper-tts` などをインストールする。オフラインで
     完結するが、CM4での速度は未検証
- **音声フォーマットは 16 kHz モノ 16bit PCM に揃える**。本体の標準はこれ
  （マイク入力も16 kHz、公式ドキュメントもアップロード音声はこの形式と明記）

**絵をきれいに撮るには**

- カメラは1280x720。近距離の紙をどこまで解像できるかは要検証
- 撮影前に頭の姿勢を明示的に指定する必要がある（待機状態では頭が下がっている。
  今回は逆に「下を向かせる」ので都合がよい）
- 手ブレは無いが、照明と影の影響は受ける。撮影位置のガイドが必要かもしれない
- `look_at_image(u, v)` で絵の中心を見るように調整できる可能性がある（`docs/tasks.md` D-1）

**プロンプト設計**

- 「キャプション」「感想」「アドバイス」を1回のリクエストでまとめて返させる
- **喋る前提なので短く**。長文だと再生が延々と続いて体験が悪い
- 感情モーションに使うため、**感情ラベルも一緒に返させる**とよい
  （例: JSONで `{"caption": …, "comment": …, "advice": …, "emotion": "proud1"}`）
  85種の名前から選ばせれば、そのまま `play_move()` へ渡せる

### トリガー（お願いするタイミングの伝え方）の候補

「絵を見て」と伝える方法をどうするか。複数を並列に受け付ける作りにしておけば、後から
足すのが楽になる。

| 方式 | 今すぐ作れるか | 壊れにくさ | 備考 |
| --- | --- | --- | --- |
| 手を叩く（音量検知） | ほぼ検証済み | ◎ ロボットに触らない | 言語非依存。STTも外部APIも不要 |
| 絵をかざしたら自動検知 | 画像判定の実装が必要 | ◎ 触らない | 操作を覚えなくてよい。実装はやや重い |
| M5Stackのボタン | プロキシAppが必要 | ○ 壊れても本体ではない | アイデア1と合流する |
| アンテナを倒す | 検証済み（B-1） | △ 引っ張りを誘発する | 実装は最短だが下記の懸念あり |
| 声で「これ見て」 | 日本語STTが未解決 | ◎ | 最も自然。アイデア2の解決待ち |

**現時点の第一候補は拍手（音量検知）。** `mic_recording_on_robot.py` でピーク・RMSを
取れているので、「ピーク > しきい値」で検知できる。ロボットに触らないため破損リスクが
なく、子どもにも「パンと叩いたら見てくれる」で伝わる。誤検知（大声、物音）は立ち上がりの
鋭さを見るか、2回連続の拍手を条件にすれば防げそう（要検証）。

**アンテナ方式の懸念。** 実装は最短だが、**アンテナをUIにすると「引っ張っていい場所」だと
教えてしまう**。子どもが触る前提だと破損が心配になる。使う場合は次の工夫が要る。

- 戻り止めが無いので倒れっぱなしになる。**発火後にトルクを入れ直して中立へ戻せば
  自動復帰スイッチになる**（バネの代わり）

```python
mini.disable_motors(ids=["left_antenna"])          # 待機: 手で動かせる
# しきい値超えで発火 → 中立へ戻す
mini.enable_motors(ids=["left_antenna"])
mini.goto_target(antennas=[0.0, 0.0], duration=0.3)
mini.disable_motors(ids=["left_antenna"])          # また待機
```

- 判定は**起動時の値を基準にした相対角度**にする（ゼロ点がズレるため）。ヒステリシスを
  入れて誤発火を防ぐ

**M5Stackのボタン方式。** 「押す」という明快さを残したい場合。壊れてもロボット本体では
なくM5Stack側なので交換が安い。机に置ける独立した装置になる。子ども向けには外付けの
大きなアーケードボタンを付けると確実に押せる。

**自動検知方式.** カメラで「紙のような四角い白い領域」を検知したら自動撮影する
（OpenCVは本体に入っている）。トリガーという概念自体をなくせるので体験は一番自然。

**進め方の案**

1. 拍手で最短に体験を作る（C-1の延長）
2. 動いたらM5Stackのボタンを追加（アイデア1のプロキシができれば自然に繋がる）
3. 日本語会話が解決したら声のトリガーを足す（最終形）

### やると面白そうなこと

- 絵を見せると首をかしげて考えるモーション（`thoughtful1`）→ 感想を喋る、という演出
- 点数をつけてもらい、高得点なら踊る（`dance1`〜`dance3`）、低評価なら落ち込む（`downcast1`）
- 描いている途中を何度か撮って、成長を褒めてもらう
- 子ども向けに、優しいアドバイスだけ返すモードを作る
- シャッターの候補は上の「トリガー」節にまとめた

### 最初の一歩

1. `camera_snapshot_on_robot.py` を流用し、頭を下げて絵を撮る（`--pitch` を正の値に）
2. 撮った画像をMacへ持ってきて、AIに読ませて日本語のコメントが返るか確認する
3. コメントをMacの `say` で音声化し、本体へ送って再生する（既存手段の組み合わせ）
4. ここまで動いたら、本体上で一連の流れを完結させる
5. 感情ラベルを返させて `play_move()` と連動させる

### 未検証・確認したいこと

- 近距離の紙がカメラでどこまで鮮明に写るか（解像度・ピント）
- 本体上でのTTS手段（外部APIか、`piper-tts` などの導入か）
- 画像1枚あたりのAPIコストと応答時間
- 撮影から発話までの体験として許容できる遅延はどれくらいか
- 絵の向き（上下逆さま、斜め）をAI側が補正できるか

## 4. 上の3つを組み合わせる案（メモ）

- M5Stack側にマイクとスピーカーがあるなら、会話の入出力をデバイス側に持たせる構成も
  ありえる（Reachy Miniは表情と動きに専念する）
- 逆に、Reachy Miniを「声で操作、デバイスで微調整」する使い分けも考えられる
- 絵の講評（アイデア3）を会話（アイデア2）の中で行う。「これ見て」と言うと撮影して
  感想を返す流れになれば、体験として自然
- M5Stackのボタンをシャッターにする（アイデア1＋3）。手が汚れていても押しやすい
